# Эпик 3 — Ежемесячные и квартальные отчёты

**Дата:** 2026-04-22
**Статус:** дизайн утверждён, к плану

## Контекст

На `/financials` уже есть форма для ежемесячных отчётов (выручка, чистая прибыль, капитал, оценки Б/С/Л 1-10, текст отчёта + запрос на разбор) и эндпоинт `POST /api/monthly-financials`. Работает частично, но с тремя проблемами:

1. **Дыра в auth.** API принимает `memberId` из тела запроса — любой залогиненный может сдать отчёт за другого.
2. **Нет уникальности.** БД позволяет вставить два отчёта за один месяц для одного юзера.
3. **Нет квартальной логики.** Поле «Капитал» всегда опциональное; правило «обязательно в марте/июне/сентябре/декабре» нигде не выражено.

## Цель

Докрутить существующий `/financials` на месте: закрыть три проблемы, добавить аккуратный edit-flow и обновить `/help`. Без интеграции с общей лентой `/reports` и без admin-UI «сдать за другого» — это задачи Эпика 4.

## Решения брейншторма

| Вопрос | Выбор |
|---|---|
| Scope | (A) — докручиваем `/financials` на месте |
| Повторный submit за месяц | (A) — upsert, юзер может править до конца месяца |
| Квартальный капитал | (B) — в неквартальные месяцы поле скрыто; в квартальные — `required` |
| Auth | (C) паттерн — main эндпоинт self-only; admin-on-behalf живёт в отдельном `/api/admin/*` эндпоинте, который пишем когда понадобится UI |
| Иконка «отредактирован» | Не делаем (YAGNI) |
| Ретро-чистка старых «капиталов в неквартальный месяц» | Не трогаем |
| `GET /api/monthly-financials` (list all) | Оставляем открытым для залогиненных — финансы внутри мастермайнда видны всем своим |

## Архитектура

Компоненты, которые меняются:

| Слой | Изменение |
|---|---|
| БД | Миграция: `UNIQUE(member_id, month)` + `updated_at` |
| API | `POST /api/monthly-financials`: `memberId` из JWT, upsert, inline-валидация полей и квартала |
| API | Новый `GET /api/monthly-financials/me?month=YYYY-MM-01` для edit-flow |
| Lib | Новый `src/lib/quarter.ts` — single source of truth для правила «квартальный месяц» |
| UI | `FinancialsClient.tsx`: edit-flow, квартал-скрытие поля, refetch при смене месяца |
| `/help` | Заменить плейсхолдер «Ежемесячный отчёт в разработке» на актуальный блок |

Что **не** меняется: Sparkline, формат валют, таблица истории, `GET /api/monthly-financials`.

## Схема БД

Текущая таблица (`src/db/schema.ts`):

```ts
monthly_financials:
  id text pk
  member_id text not null -> members.id
  month text not null           // "YYYY-MM-01"
  revenue, net_profit, capital real
  score_business/family/personal integer
  report_text, request_text text
  created_at text not null
```

**Изменения:**

1. Новая колонка `updated_at text not null default (current_timestamp)` — когда запись последний раз редактировали (для upsert-видимости). Для существующих строк заполнить значением `created_at`.
2. Новый уникальный индекс `uniq_monthly_member_month` на `(member_id, month)`.
3. Pre-migration check: выполнить `SELECT member_id, month, COUNT(*) FROM monthly_financials GROUP BY member_id, month HAVING COUNT(*) > 1`. Если дубликаты найдены — ручное решение (оставить самый свежий по `created_at`) до `CREATE UNIQUE INDEX`. В БД сейчас 3 члена, дубликатов, скорее всего, нет, но страхуем.

**Формат `month`** остаётся `YYYY-MM-01`.

**Квартальная валидация** — на уровне API (zod + доменная логика в `src/lib/quarter.ts`), не DB CHECK. Причина: CHECK-выражение на основе `strftime('%m', month)` хрупко и ломается при правке формата.

## API

### `POST /api/monthly-financials`

**Auth:** обязательна сессия (JWT из cookie). Без сессии → 401. `memberId` берётся из сессии, поле в теле запроса игнорируется.

**Body (inline-валидация по стилю кодбазы):**

| Поле | Тип | Правило |
|---|---|---|
| `month` | string | `/^\d{4}-\d{2}-01$/` |
| `revenue` | number | обязательно |
| `netProfit` | number | обязательно |
| `capital` | number \| null | см. ниже |
| `scoreBusiness` | int | 1..10 |
| `scoreFamily` | int | 1..10 |
| `scorePersonal` | int | 1..10 |
| `reportText` | string | min 1 |
| `requestText` | string \| null | опционально |

**Правило капитала:**

- `isQuarterEnd(month)` истинно для месяцев с индексом `{2, 5, 8, 11}` (март, июнь, сентябрь, декабрь).
- Если квартал и `capital == null` → 400 `"Капитал обязателен в квартальный месяц"`.
- Если не квартал и `capital != null` → сервер молча выставляет `null` (данные за неквартальные месяцы не храним — они не имеют смысла).

**Поведение (upsert):** транзакция `INSERT ... ON CONFLICT(member_id, month) DO UPDATE`:

- Если записи нет — вставка: новый `id`, `created_at = now`, `updated_at = now`.
- Если есть — обновление всех бизнес-полей, `created_at` не трогаем, `updated_at = now`.

**Ответы:**

- `200` — upsert прошёл, в теле обновлённая запись.
- `400` — zod или валидация капитала не прошла.
- `401` — нет сессии.

### `GET /api/monthly-financials/me?month=YYYY-MM-01`

Новый эндпоинт. Auth обязательна. Возвращает запись текущего юзера за указанный месяц или `null`.

Нужен клиенту, чтобы решить «Новый отчёт» vs «Редактировать» и предзаполнить форму.

### `GET /api/monthly-financials`

Оставляем как есть. (Рассмотрим auth-scope в Эпике 4, если потребуется.)

### Admin-on-behalf

В этом эпике **не реализуем**. Когда появится нужда (админ хочет ввести цифры за забывчивого участника) — отдельный `POST /api/admin/monthly-financials` с явной проверкой `isAdmin`, по паттерну `/api/admin/members`, `/api/admin/activate-goals`.

## `src/lib/quarter.ts`

Single source of truth для правила «квартальный месяц». Используется и сервером, и клиентом.

```ts
export function isQuarterEnd(monthIso: string): boolean {
  // monthIso: "YYYY-MM-01"
  const m = Number(monthIso.slice(5, 7)) - 1;
  return m === 2 || m === 5 || m === 8 || m === 11;
}
```

Юнит-тесты (vitest): граничные месяцы (янв-дек), год-високос в 2024/2028 не влияет, невалидный формат.

## UI: `/financials` (FinancialsClient.tsx)

**Открытие формы:**

- По-умолчанию `month` = текущий (напр. `2026-04`).
- При открытии и при смене `month` клиент делает `GET /api/monthly-financials/me?month=...`.
- Если ответ — объект: заголовок «Редактировать отчёт за _LLLL yyyy_» (на русском), поля предзаполнены, кнопка **«Сохранить изменения»**.
- Если `null`: заголовок «Месячный отчёт», пусто, кнопка **«Сохранить отчёт»**.

**Поле «Капитал»:**

- Рендерится только если `isQuarterEnd(monthIso) === true`.
- Label: **«Капитал на конец квартала, ₽»**.
- `required`, `type="number" step="0.01"`, без пометки «опционально».
- В неквартальные месяцы — поле не показано вообще.

**Остальные поля:** как сейчас (`revenue`, `netProfit` — `required number`; `score_*` — `required number 1..10`; `reportText` — `required textarea`; `requestText` — опционально).

**Валидация на фронте** дублирует серверную. Серверная — финал.

**Submit:** POST без `memberId` в body. После успеха — `router.refresh()`, форма закрывается.

**Error UX:** 400 с сервера → inline-сообщение красным над кнопкой сохранения. Не теряем введённые данные.

## `/help`

Убрать плейсхолдер «Ежемесячный отчёт в разработке». Добавить блок:

> ## Ежемесячный отчёт
>
> Каждый участник сдаёт отчёт раз в месяц через страницу **Финансы**.
>
> **Что указываем:**
> - Выручка (валовая) и чистая прибыль за месяц, ₽
> - Оценки по сферам: Бизнес / Семья / Личное (1-10)
> - Текст отчёта по сферам
> - Запрос на разбор (если есть)
>
> **Капитал** сдаём только в конце квартала — в марте, июне, сентябре и декабре. В эти месяцы поле обязательное. В остальные — оно скрыто.
>
> **Редактировать** можно в любой момент: сохраняешь заново, запись обновляется. Финалом считается последняя сохранённая версия.

## Тесты

**Юнит (vitest):**

- `src/lib/quarter.ts` — граничные значения, валидность формата.
- Логика upsert и валидации вынесена в тестируемую функцию в `src/lib/monthlyFinancials.ts`:
  - happy path (insert)
  - upsert (второй вызов обновляет ту же строку, `created_at` не меняется)
  - 400 в квартальный месяц без капитала
  - `capital != null` в неквартальный месяц — в БД запишется `null`
  - минимальные поля (`reportText` пустой → ошибка, score вне 1..10 → ошибка)
- API `GET /api/monthly-financials/me`:
  - возвращает запись юзера из сессии
  - возвращает `null` если нет
  - 401 без сессии

**Ручная проверка:**

- Форма на `/financials`: смена месяца → подхватывается предыдущий отчёт; квартал ↔ не квартал → поле капитала появляется/исчезает.
- `/help`: блок виден, старый плейсхолдер убран.

## Риски

- **Миграция на проде.** Если в `/root/lumm/data/*.db` есть дубликаты `(member_id, month)` — `CREATE UNIQUE INDEX` упадёт. План: SELECT-проверка перед индексом, при находке — ручное решение (оставить самый свежий по `created_at`).
- **UX edit-flow при смене месяца.** Если юзер ввёл данные, а потом передумал и сменил месяц — refetch затрёт введённое. Считаем это приемлемым: в реальности юзер выбирает месяц первым шагом. При желании — отложенная проверка «dirty form → confirm» в будущем.
